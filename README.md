# PersonalManagement

Личная система управления направлениями, измеримыми целями, проектами, задачами и календарём. Версия **MVP 0.1**.

## Возможности

- Календарь по неделям с часовой сеткой, событиями и запланированными задачами.
- Направления → проекты → измеримые цели и конкретные задачи.
- Входящие, список дел, матрица Эйзенхауэра (P1–P4).
- Единая карточка редактирования и связь задач с направлением, проектом и целью.
- PostgreSQL на стороне Bothost и JSON-экспорт данных.

## Переменные для Bothost (PostgreSQL)

Приложение использует **только PostgreSQL**. Создайте БД в панели Bothost и
скопируйте **полную** строку подключения в секретную переменную окружения
`DATABASE_URL` (например `postgresql://user:password@host:5432/database`).
Не помещайте реальную строку с паролем в GitHub, логи или скриншоты.

| Переменная | Значение |
|---|---|
| `DATABASE_URL` | **Полная строка подключения PostgreSQL, предоставленная Bothost** |
| `APP_PASSWORD` | Уникальный длинный пароль личного кабинета PersonalManagement |
| `APP_USERNAME` | `owner` (или другое имя пользователя) |
| `PORT` | **`3000`** |

В Bothost используйте корневой `Dockerfile`, исходники `main`, внутренний
порт **3000**, HTTPS и веб-домен. `DATABASE_PATH` не используется и должен быть
удалён из переменных приложения, если был установлен ранее. Приложение само
создаёт таблицы в PostgreSQL при старте. Telegram-переменные пока не нужны.

**Внимание при обновлении:** переход с SQLite на PostgreSQL не переносит
старые записи автоматически. Если вы ранее заполняли SQLite, нужно сначала
сделать её экспорт и отдельно импортировать в PostgreSQL. Если сервер ещё
не использовался, создаётся пустая PostgreSQL-база.

## Запуск через Docker

1. Скопируйте `.env.example` в `.env`. Установите **уникальный сильный** `APP_PASSWORD`.
2. Запустите `docker compose up --build -d`.
3. Откройте `http://localhost:3000` (на внешнем сервере **только через HTTPS**).
4. Введите логин из `APP_USERNAME` (по умолчанию `owner`) и пароль `APP_PASSWORD`.

Для Bothost: подключите GitHub-репозиторий как приложение с собственным Dockerfile, выберите ветку **`main`**, установите **порт `3000`**, настройте HTTPS-домен и секретные переменные `APP_PASSWORD` и **`DATABASE_URL`** из PostgreSQL, созданной в Bothost. Код и файлы сайта находятся в `/usr/src/personalmanagement`, а данные — в управляемой PostgreSQL. Тома для PostgreSQL не нужны.

## Разработка

Backend (Python 3.12):

```bash
cd backend
python -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
APP_PASSWORD=dev-only DATABASE_URL=postgresql://USER:PASSWORD@HOST:5432/DATABASE STATIC_DIR=../frontend/dist uvicorn app:app --reload --port 3000
```

Frontend (Node.js 22):

```bash
cd frontend
npm install
npm run dev
```

Откройте порт Vite (5173), который проксирует `/api` в FastAPI (3000).

Тесты: `cd backend && pytest -q`. Проверка frontend: `cd frontend && npm run build`.

## Как связаны сущности

- **Направление**: постоянная сфера жизни.
- **Проект**: ограниченный результат, может относиться к направлению.
- **Цель**: измеримый показатель с периодом и прогрессом, относится к направлению и/или проекту.
- **Задача**: конкретное действие; ссылки на направление/проект/цель необязательны.
- **Событие**: событие с началом и окончанием; запланированная задача показывается в календаре без дублирования события.

Матрица: P1 = важно и срочно; P2 = важно, не срочно; P3 = срочно, не важно; P4 = не важно и не срочно.

## Безопасность и данные

- **Приложение без HTTPS в интернет не выставлять.** В MVP используется HTTP Basic Auth, защищённый TLS при внешнем доступе.
- База **не в GitHub и не в контейнере**: это отдельный PostgreSQL-сервис Bothost. Подключение определяется только секретной переменной `DATABASE_URL`.
- Перед обновлениями и регулярно делайте резервную копию PostgreSQL средствами Bothost или через `pg_dump` (храните архив отдельно от приложения). JSON-экспорт доступен из интерфейса и API.
- Это личный MVP, не многопользовательский продукт. В нём пока нет ролей, OAuth, двусторонней синхронизации Google Calendar, push-уведомлений, drag-and-drop и автоматических повторений. Поле повторения зарезервировано для следующих этапов.
- Время первой версии хранится как локальное календарное время. Для синхронизации между часовыми поясами потребуется переход на UTC + IANA timezone.

## GitHub Pages: открытый тестовый стенд

В публичном репозитории Pages используется **только для просмотра и настройки интерфейса**, без FastAPI и PostgreSQL.

1. В GitHub перейдите в **Settings → Pages → Build and deployment → Source: GitHub Actions**.
2. Workflow `.github/workflows/pages.yml` соберёт frontend с `VITE_DEMO_MODE=true` и `VITE_BASE_PATH=/PersonalManagement/`.
3. После успешной публикации адрес стенда: `https://urbanvdk-byte.github.io/PersonalManagement/`.

В режиме Pages примерные направления, проекты, задачи и цели хранятся **только в localStorage текущего браузера**. Встроены JSON-экспорт и кнопка сброса примеров. Удаление браузерных данных или открытие другого браузера может привести к потере записей; синхронизации между устройствами нет. Не используйте публичный стенд для паролей, финансовых, медицинских или других конфиденциальных данных.

Режим Pages не затрагивает production: Docker по-прежнему собирает Vite без VITE_DEMO_MODE и использует FastAPI + PostgreSQL. Интерфейс доступен для теста; серверные функции необходимо проверять отдельно при размещении на Bothost.

## Календарь: этап 1

- В мини-календаре зажмите дату **мышью или пальцем** и протяните до конца периода. Основная часовая сетка покажет все дни диапазона (с горизонтальной прокруткой для длинного диапазона). Один клик открывает выбранный день. Кнопка × очищает выделение.
- Сетка отображает все 24 часа; каждый час имеет высоту **62 / 1.5 = 41.3 px**. При открытии текущая дата прокручивается к текущему часу.
- **Красная линия** с точкой показывает текущее время на сегодняшней дате и обновляется каждые 30 секунд.
- У задачи можно выбрать один из восьми цветов. Левая вертикальная полоса — отдельный цвет приоритета P1–P4.
- Направлению можно назначить emoji из списка или вставить свой. Emoji появляется справа сверху на задаче в календаре.
- Старые записи браузерного демо не удаляются; при отсутствии нового поля показываются безопасные значения по умолчанию. Для PostgreSQL добавлены идемпотентные миграции существующих таблиц.

## Исправления мини-календаря и формы задачи

- Кнопка «Сегодня» есть внутри мини-календаря и возвращает текущую дату и неделю.
- Продолжительность задачи: **минимум 30 минут**, далее **шаг 15 минут**. Стрелки числового поля используют шаг 15; ручной ввод остальных чисел не принимается.
- На коротких карточках (30 и 45 минут) отображается **название в одной строке**; время доступно при наведении на карточку и для экранных дикторов.
- Emoji на карточке задачи и в списке направлений показываются без цветного фона и рамки.
- Для новых задач дата и время обязательны: пока поле пустое, оно отмечено красным и кнопка сохранения заблокирована; есть явная кнопка «Отмена». Аналогичное правило применяется на сервере и в Pages-демо, поэтому несохранённые задачи не исчезают незаметно.
- Старые задачи, созданные без времени до введения правила, остаются в хранилище и могут быть отмечены выполненными или удалены.

## Прямое редактирование календаря — этап 2

- **Мышь:** зажмите тело задачи и перенесите на другой день или час. Выделенное положение отображается полупрозрачной карточкой, после отпускания сохраняется.
- **Мобильный телефон:** задержите палец на задаче примерно 0,4 секунды, затем протяните. Короткое касание открывает карточку без изменений.
- **Верхний край задачи:** зажмите и протяните, чтобы изменить начало и длительность, сохраняя окончание.
- **Нижний край:** зажмите и протяните, чтобы изменить длительность, сохраняя начало.
- Шаг перемещения и изменения длительности — **15 минут**, минимальная длительность — **30 минут**.
- Данные сохраняются через тот же API/PostgreSQL, а на GitHub Pages — в localStorage браузера. При ошибке записи исходная задача остаётся прежней.
- При создании направления больше нет выбора цвета, а на карточке направления нет повторяющейся метки «Направление».

## Календарь: расположение пересекающихся задач

- События и задачи на одинаковое время показываются в **соседних колонках**, без наложения карточек друг на друга.
- При частичном пересечении сохраняются независимые колонки. Группы задач, не пересекающиеся по времени, вновь занимают всю ширину дня.
- Соседние свободные колонки используются для расширения карточки, когда они не заняты одновременными задачами.
- Если задач одновременно много, отдельный день становится шире, а календарь прокручивается горизонтально, сохраняя читаемость и все жесты переноса/изменения длительности.
- В расчёт входят как задачи, так и события; **данные, время, приоритеты и сохранение не меняются**.

## Этап 3: повторяющиеся задачи

В карточке задачи появился выбор «Повторять»: не повторяется / ежедневно / еженедельно / ежемесячно / ежегодно. При необходимости задайте «Повторять до».

Календарь разворачивает повторения **только для видимых дней**, не создавая строки задачи для каждого дня. Изменения и отметки выполнения отдельных повторов хранятся в компактных исключениях:
- **Только это повторение** — отдельная дата/время, длительность, свойства или завершение; остальные дни не затрагиваются;
- **Это и следующие** — создаёт новую серию с выбранной даты, ограничивая предыдущую; изменения уже существовавших будущих исключений переносятся;
- **Вся серия** — редактирует исходную задачу; изменение времени не передвигает дату начала серии.

Удаление повторения поддерживает те же области действия. При перетаскивании или растягивании **повторяющегося экземпляра** меняется только этот экземпляр, а не серия.

Ежемесячный повтор 31-го числа попадает на последний день февраля, апреля и других коротких месяцев; ежегодный повтор 29 февраля попадает на 28 февраля вне високосных лет.

В PostgreSQL создаётся таблица `task_occurrences` с уникальной парой `task_id + occurrence_date`. Для старых баз `tasks.recurrence_until` добавляется без удаления существующих задач. Экспорт JSON включает и серии, и исключения. В GitHub Pages те же данные сохраняются в текущем localStorage (старые данные не сбрасываются).

## Tasks and project containers (November 2026)

- In **Calendar**, a new task requires a real date/time and is scheduled immediately. In **All tasks**, **Inbox**, and a project, the time can remain empty; such tasks are saved and excluded from every calendar view, even when they have a deadline.
- A repeating task always needs a dated occurrence to anchor its rule.
- **All tasks** displays separate collapsible cards for P1–P4 using the Eisenhower layout, plus collapsed **Completed** and optional **Cancelled** history. Search still filters across all groups.
- Clicking a project opens its container with related tasks, measurable goals, events, progress, and directions. **Edit project** is a separate button.
- Projects can have zero, one or multiple directions. The server stores membership in `project_areas` while keeping the legacy `projects.area_id` field synchronized for compatibility; on upgrade, old associations are safely copied. GitHub Pages stores `area_ids` on the existing project records without resetting localStorage.

## Объединённое планирование — этап 4

- Под месячным календарём справа (на телефоне — под часовой сеткой) находится разворачиваемый блок **«Незапланированные»**. Перетащите задачу мышью или удерживайте палец ~0,4 секунды и переместите карточку в часовую сетку. Сохранение выполняется только после отпускания над рабочим днём.
- **План дня** справа от сетки: три самых приоритетных дела, нагрузка по задачам и событиям из расчёта 8 ч, просроченные задачи и действия «Завтра». Это ориентир, а не автоматический выбор за владельца.
- Строка быстрого ввода над календарём работает из любой вкладки: напишите задачу, Enter, она сохранится в общем списке без времени.
- В карточке календарной задачи есть стрелка «Завтра». На мобильном **двойное короткое касание** переносит задачу на ближайшее завтра с сохранением часа. Обычное короткое касание открывает редактор, удержание запускает перетаскивание; изменение повторяющейся задачи затрагивает лишь выбранный экземпляр. «Убрать из календаря» есть в редакторе одиночной задачи.
- В задаче есть чек-лист; в проекте — этапы с датами, следующий приоритетный шаг и история изменений. Это отдельные таблицы с внешними ключами, без миграции старых записей.
- Telegram: сервер автоматически отправляет только три отчёта при наличии `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`. Часовой пояс задаётся `PM_TIMEZONE` (по умолчанию Europe/Moscow). Утренний — ежедневно в 08:00, недельный — пятница в 21:00 (за понедельник–пятницу, сравнение с теми же днями прошлой недели), месячный — первое число следующего месяца в 08:05. При запуске позже времени отчёта возможна отправка в тот же день. PostgreSQL хранит ключи отправки. Старые режимы `evening` и `reminders` отключены. Плановые часы не являются фактическими, история переносов и достижений целей пока не сохраняется. Предпросмотр без отправки: `python telegram_digest.py --mode weekly --dry-run` (также `morning`, `monthly`). Токен задавайте только в приватных переменных Bothost.

## Защита входа и редактирования (ноябрь 2026)

- Основной вход — пароль через HTTP Basic Auth, обязательно с HTTPS. Авторизация через Telegram запланирована отдельно и ещё не реализована.
- После 5 неправильных паролей с одного IP за 15 минут сервер блокирует попытки на 15 минут (HTTP 429, заголовок Retry-After). Счётчики хранятся в PostgreSQL и переживают рестарт. Это не заменяет защиту от распределённого перебора на reverse proxy.
- При работе за reverse proxy правильно настройте доверенные прокси для Uvicorn (FORWARDED_ALLOW_IPS); клиентскому X-Forwarded-For напрямую доверять нельзя. Иначе несколько посетителей могут ошибочно учитываться как один IP адрес прокси.
- У сущностей появился revision. Для изменений веб-клиент передаёт If-Match со значением текущей версии. Устаревшие редактирование и удаление получают HTTP 409 вместо молчаливой перезаписи. Старые API-клиенты без заголовка пока поддерживаются, но не получают защиту от конфликтов.
- Схема существующей БД обновляется без удаления данных. Перед деплоем обязательно сделайте консистентную резервную копию базы.


## Offline-first: работа без интернета

В production-сборке браузер сохраняет статический интерфейс через Service Worker и
снимок данных в IndexedDB (`personalmanagement-offline-v1`). После первого **успешного**
входа по HTTPS календарь, задачи, цели, проекты, события, повторения, чек-листы
и этапы можно просматривать и редактировать без сети — в той же вкладке или
через обычный ярлык сайта на телефоне.

Изменения сразу записываются **одной транзакцией IndexedDB вместе с журналом
неотправленных операций**. Сервер обрабатывает очередь по порядку через
`POST /api/offline/execute`: результат мутации и идентификатор выполненной
операции записываются в одну транзакцию PostgreSQL. Повторная отправка после обрыва
возвращает прежний результат и не создаёт дублей. Клиент преобразует временные
отрицательные ID в реальные ID, сохраняя связи между записями.

После восстановления связи синхронизация выполняется при открытии или
возвращении в окно, по событию `online` и каждые 30 секунд при открытой странице.
В интерфейсе отображаются количество несинхронизированных действий и состояние
связи. Серверная проверка `revision` не позволяет молча затереть правки из
другого устройства. При конфликте отправка останавливается: можно сознательно
оставить локальную версию либо **после JSON-экспорта** отказаться от всех ожидающих
локальных изменений и загрузить серверную копию.

**Ограничения и правила безопасности:**

- Первый запуск офлайн невозможен: сначала откройте обновлённый сайт **онлайн**
  и дождитесь загрузки. Подключение должно быть HTTPS (или localhost).
- Синхронизация при полностью закрытом браузере или заблокированном телефоне
  **не гарантируется**; при следующем открытии менеджер продолжит работу.
- Устройство может очистить данные браузера (особенно в режиме экономии места).
  Пока имеются неотправленные операции, не очищайте данные сайта и не удаляйте
  браузер. Периодически сохраняйте JSON-экспорт вне телефона.
- Локальная копия может быть доступна любому, кто имеет доступ к разблокированному
  телефону и профилю браузера. Экранная блокировка телефона обязательна; не
  используйте эту функцию на общем устройстве.
- Синхронизация не обходит пароль: если сервер запросил повторную авторизацию
  или временно заблокировал вход, локальные изменения сохраняются до успешного
  входа и синхронизации.
- При ручном выборе серверной версии отменяются **все** ожидающие локальные
  изменения, а не только одна запись. Перед этим скачайте локальную JSON-копию.
- GitHub Pages по-прежнему является *отдельным демостендом* в localStorage:
  его данные не синхронизируются с сервером. Service Worker позволяет открывать
  этот стенд без сети, но не превращает его в рабочую учётную запись.

Для локальной проверки полной production-цепочки:
`npx playwright test --config=playwright.offline.config.ts` из `frontend/`
при запущенном FastAPI на `127.0.0.1:3000` с тестовым паролем
`offline-test-password` и обслуживанием собранной директории `frontend/dist`.
Проверка также запускается в GitHub Actions (job `offline-e2e`).

## Push-напоминания

На каждом устройстве откройте PersonalManagement по HTTPS, откройте боковое меню и нажмите «Включить напоминания», затем разрешите уведомления. На телефоне пункт находится в меню «Ещё». Сервер автоматически хранит VAPID-ключи и подписки в PostgreSQL; новые переменные окружения не обязательны. Время push-напоминаний интерпретируется в часовом поясе устройства, который браузер обновляет при открытии приложения. Для старых подписок до обновления применяется PM_TIMEZONE. Telegram сохраняет собственный PM_TIMEZONE. Кнопка «Проверить уведомление» отправляет тест только на текущее устройство. Единственный тип напоминаний — за 60 минут до начала незавершённой задачи, независимо от приоритета. При кратковременном сбое допускается отправка в течение следующих пяти минут, позднее старое напоминание пропускается. Изменённое время учитывается заново; без синхронизации офлайн-изменений сервер о них не знает. Уведомления и их отображение на заблокированном экране зависят от разрешений браузера и ОС; на iOS нужен установленный на домашний экран PWA и поддержка Web Push. Отключение — той же кнопкой. Данные подписок и приватный ключ не включаются в экспорт JSON; при переносе БД сохраните таблицы push_vapid, push_subscriptions, push_sent. Telegram-отчёты независимы.
